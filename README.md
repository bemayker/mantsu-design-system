# Mantsu Design System

React component library + design tokens for the Mantsu MES UI, extracted from
the Figma Design System (`kN9ZMAZ7NrhNp0iu8gpzEC`). Built with Storybook 8,
Tailwind CSS, and TypeScript.

Published as **`@bemayker/mantsu-design-system`** on GitHub Packages. This repo is the
single source of truth for the design system: for the team (a browsable component
catalogue) and for the four Mantsu frontends, which install it.

## Getting started

```bash
npm install
npm run storybook      # dev server on :6006
npm run build-storybook
npm run typecheck
npm test
npm run build          # dist/: ESM, CJS, types, styles.css
```

## Structure

```
src/
  tokens/tokens.ts        # canonical design tokens (colors, type, spacing, shadows)
  tailwind-preset.ts      # the Tailwind theme, mirroring tokens.ts
  components/             # React components, token-driven via Tailwind
  components/icons/       # Mantsu module icons, published as /icons
  stories/                # Storybook stories, grouped by category
  styles/package.css      # published as /styles.css: webfont + root font-family
  styles/globals.css      # Storybook entry: package.css + Tailwind layers
  test/                   # Vitest: package contract + render smoke tests
examples/consumer/        # bare Vite app that installs the package, run in CI
tailwind.config.ts        # consumes the preset, so the theme has one definition
DESIGN-SYSTEM.md          # compact reference for Cursor / codegen
VENDORING.md              # the older vendoring route, still in force for six copies
CHANGELOG.md              # one entry per released version
docs/suite-manifest.md    # the suite manifest contract, normative for four repos
```

## Installing it in an app

The package is private to the `bemayker` organisation, so npm needs to be pointed at
GitHub Packages and given a token.

**1. `.npmrc` in the app repo** (committed; it contains no secret):

```
@bemayker:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
```

**2. Locally**: create a GitHub personal access token (classic) with the `read:packages`
scope and export it. Do not put the token in the repo.

```bash
export NODE_AUTH_TOKEN=ghp_...
npm install @bemayker/mantsu-design-system
```

**3. In GitHub Actions**: the built-in token can read this package only once the
consuming repository has been granted access to it. A package published by this repo
belongs to this repo, and another repo's `GITHUB_TOKEN` gets

```
npm error 403 Permission permission_denied: read_package
```

until someone adds it. Two ways to fix that, either is enough:

- set the package's visibility to **Internal** (package page -> Package settings ->
  Change visibility), which makes it readable by every repository in the organisation;
- or add each consuming repository under **Manage Actions access** with the Read role.

Both are one-time, manual, and neither can be done from a workflow. Verified the hard
way in NAV-7: an unprivileged probe from `mantsu-core` was refused before the grant.

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: 20
    registry-url: https://npm.pkg.github.com
    scope: '@bemayker'
- run: npm ci
  env:
    NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

**4. In a Dockerfile**: pass the token as a build secret, never as an `ARG` or `ENV` —
both of those persist in an image layer and leak the token to anyone who can pull it.

```dockerfile
# syntax=docker/dockerfile:1.7
RUN --mount=type=secret,id=npm_token \
    NODE_AUTH_TOKEN="$(cat /run/secrets/npm_token)" npm ci
```

```bash
docker build --secret id=npm_token,env=NODE_AUTH_TOKEN .
```

## Styling: the Tailwind preset

The package ships JavaScript, **not** a compiled Tailwind stylesheet. Shipping one would
duplicate Tailwind's base layer and fight the app's own build, so the utility classes our
components reference are generated by the consuming app's Tailwind. That means two things
in the app's `tailwind.config.js`:

```js
const mantsu = require('@bemayker/mantsu-design-system/tailwind-preset');

module.exports = {
  presets: [mantsu],
  content: [
    './src/**/*.{ts,tsx}',
    './node_modules/@bemayker/mantsu-design-system/dist/**/*.js', // required
  ],
};
```

Miss the second `content` entry and the components render unstyled, with no error.

`@bemayker/mantsu-design-system/styles.css` carries only what Tailwind cannot generate:
the Lato webfont and the root font-family. Import it once at the app entry point.

An app that adopts the preset should delete its hand-copied token block; keeping both is
how the two drift. `examples/consumer/` is the worked example, and it declares no tokens
of its own on purpose.

## Entry points

| Import | Contents |
|---|---|
| `@bemayker/mantsu-design-system` | components and tokens |
| `@bemayker/mantsu-design-system/tokens` | tokens only, no React |
| `@bemayker/mantsu-design-system/tailwind-preset` | the Tailwind theme |
| `@bemayker/mantsu-design-system/icons` | Mantsu module icons |
| `@bemayker/mantsu-design-system/styles.css` | webfont + root font-family |

`react` and `react-dom` are peer dependencies (`^18.3`), so a consuming app never ends up
with two copies of React.

`lucide-react` is deliberately not a dependency. Generic pictograms come from the app and
are passed to components as `ReactNode`; only the suite's own module marks live here.

## Versioning and releasing

Semantic versioning, against the **public API**: the exported components and their props,
the token names, the Tailwind preset's theme keys, and the `exports` map.

- **Major** — removing or renaming any of those, or changing a default that alters how an
  existing app renders.
- **Minor** — new components, new optional props, new tokens.
- **Patch** — fixes that leave the API alone.

To release:

1. Bump `version` in `package.json` and add a `CHANGELOG.md` entry.
2. Merge to `main`.
3. `git tag v1.2.3 && git push origin v1.2.3`.

The tag triggers `.github/workflows/publish.yml`, which typechecks, tests, builds, refuses
to publish if the tag disagrees with `package.json`, and then publishes. Storybook still
deploys to GitHub Pages on every push to `main`, unchanged.

## Contributing a change

A change requested by a consuming app lands **here** first, with a story that demonstrates
it, and the app then bumps the version. Never only in the app: the next app inherits the
original bug otherwise. Token values come from Figma and are regenerated, not hand-edited,
and `tailwind-preset.ts` must stay in step with `tokens.ts` — a test asserts that it does.

## Vendoring

Six components were vendored into apps before this package existed (`dsTree`, `dsTable`,
`dsColorPicker`, `dsDropdown`, `dsSwitch`, `DataTable`). They stay vendored under
**[VENDORING.md](VENDORING.md)** until a separate migration story. New components are
consumed from the package.

## Cross-repo contracts

`docs/suite-manifest.md` is the normative contract for the **suite manifest**, the payload
that tells a Mantsu frontend which apps exist in a landscape. It is here rather than in an
app repo because all four frontends already depend on this one, and the manifest is a
protocol between six moving parts. It ships with a JSON Schema for producer validation,
three worked examples, and `parseManifest`, exported from the package root, which is the
only supported way to consume it. Backends implementing it (`mantsu-core`,
`mantsu-order-cockpit`, `mantsu-downtimes`, `mantsu-lists`) link to that document rather
than restating it.

## Tokens

Colors, the Lato type scale, shadows, and the primary gradient are extracted
verbatim from Figma. Tailwind utility classes map 1:1 to them
(e.g. `bg-midnight`, `text-h2`, `bg-primary-gradient`, `shadow-mantsu-lg`).
See `DESIGN-SYSTEM.md` for the full table.

## Components

Form: Button, Input, DatePicker, TimeField, DateTimePicker, Switch, Checkbox, Radio
Data display: Badge, Tag, Card, OptionCard, Table, EmptyState
Navigation: Tabs, Breadcrumbs, Sidebar, TopNavBar, Tree, SuiteNav, SettingsScopePage
Feedback: Modal, SideDrawer, Toast, Tooltip
Charts: PieChart, GaugeChart, ProgressBar

`SuiteNav` is the suite navigation rail and `SettingsScopePage` is the settings chrome.
Both take the suite manifest, this app's own items or rows, and a `renderLink` that
supplies the app's own router link; they own no state, fetch nothing and translate
nothing. See their Storybook stories, and `docs/suite-manifest.md` for the payload they
render from.

`DatePicker`, `TimeField` and `DateTimePicker` are the only date and time inputs a Mantsu
app should use: the native `type="date"`, `type="time"` and `type="datetime-local"`
inputs render in the operating system's locale, not the app's language (CORE-FB-23).
They take and return ISO strings, never `Date` objects, and put `testId` on the input
the user types into.

`scopesFromManifest` builds the settings scope column from a manifest. Use it rather
than assembling the list per app: it is where the rules live about which scopes exist
in a given landscape.

The module icons live at `@bemayker/mantsu-design-system/icons` and are generated from
the handoff's SVG sheet by `scripts/generate-module-icons.mjs`. Do not hand-edit them:

```bash
node scripts/generate-module-icons.mjs [path-to-mantsu-module-icons.svg]
```
